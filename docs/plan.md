# Plan and status

Where the project stands, what's decided, and what comes next. Keep this current with each step; the chat that produced it isn't the record.

## Status

**Phases 1 to 3 work on the owner's dongles (as of 2026-11-21):** GPS to Traccar over Wi-Fi and LTE (SIM7070G, acknowledged), Wi-Fi first with a search back-off, records and logs on the SD card, sleep while parked (OBD or USB power) with motion wake, trips started only after the motion sensor felt the car move. A day in the Volvo found standby's safe-mode wakes (fixed the same evening). The Home Assistant integration configuration (compact batches to a webhook, raetha/ha-freematics) works on the second dongle and is ready for side-by-side trips with Traccar. On 2026-11-22 the design was reworked before those trips (below): trips decided once per car, uplinks with pluggable protocols, the motion sensor in C++ with impact detection and temperature, cellular signal reported, and a GNSS restart, all waiting for a bench check (bench-tests.md, 7d); the native-API Home Assistant configuration compiles but hasn't been tried. Vehicle data (phase 4) has a listening test built and nothing that sends. The dongles have SIM7070G modules on Hologram (APN `hologram`), pay as you go: the stock telelogger's 10 to 15 KB on a typical day is the benchmark.

## Goal and requirements

Replace the Freematics telelogger firmware on two ONE+ Model B dongles with ESPHome. The stock firmware loses data and has triggered warnings on the Volvo and the Subaru.

| # | Requirement | Priority |
| --- | --- | --- |
| R1 | Cache every sample on the device while offline, replay it later with the original timestamps | Must |
| R0 | Keep cellular data to the bare minimum: every design choice is weighed by its bytes on LTE | Must |
| R2 | Deliver to Traccar (the owner's choice) or Home Assistant, with delayed fixes stored at their real time | Must |
| R3 | GPS position as a Home Assistant device_tracker | Must |
| R4 | Wi-Fi preferred over cellular, several known networks | Must |
| R5 | Read the vehicle without upsetting it: passive only, nothing sent on the bus | Must |
| R6 | VIN, battery voltage, fuel level and the PIDs the telelogger reported | Should |
| R7 | IMU data | Could |

## Decisions

- **Traccar first, over Teltonika GH3000 UDP.** The native API costs far too much data for a pay-as-you-go plan (about 650 KB against 15 KB on a workday). The device sends compact, timestamped, acknowledged records straight to the owner's Traccar; no tunnel, no Home Assistant traffic from the car. GH3000 because it's the densest format Traccar decodes and Traccar acknowledges each packet. (2026-11-19, replacing the earlier native-API-first decision)
- **The repo keeps every configuration as an example** with its pros, cons and data use ([configurations.md](configurations.md)): Traccar, Home Assistant's integration and Home Assistant's native API now, MQTT maybe later. (2026-11-19, 2026-11-21)
- **Native API configuration:** the native API dialled from the device (`api: outgoing_connection:`, HA 2026.10+) through WireGuard, not MQTT. (2026-11-19)
- **Wi-Fi first like the telelogger:** LTE is switched off while a known Wi-Fi network is connected. (2026-11-19)
- **Data is the top constraint.** Update frequency and triggers follow the telelogger's where they make sense and are all substitutions. Position only while moving; vehicle values (later) once per stop. (2026-11-19)
- **The vehicle bus is read passively only:** no OBD requests, no writes. Active polling may be tested later, carefully. (2026-11-19)
- **Home Assistant through its own integration** (raetha/ha-freematics, HACS: one integration per repo): the dongle posts compact batches (`compact.h`, about 11 bytes a record) to a webhook per dongle over HTTPS, Nabu Casa's or Home Assistant's own address, never a port opened at home. Home Assistant keeps no back-dated states, so each batch moves the device to its newest record and trips arrive as events with their recorded times; replayed sensor values could become long-term statistics later. The same `tracker_uplink` component serves Traccar and Home Assistant, side by side if wanted. (2026-11-21)
- **One repo for ESPHome work** (this one, on `dev`); whether generic components move elsewhere is decided later. (2026-11-19)
- **The examples are paste-and-build**: a device config pasted into ESPHome Device Builder fetches the packages and components from GitHub. (2026-11-19)
- **Build one piece at a time**, YAML stopgap first, then a component that replaces it.
- **Sleep while parked is deep sleep**, not the stock firmware's awake standby: the ESP32 sleeps and checks the 12 V voltage and the motion sensor's latched flag once a minute; the module is powered down and the co-processor put in low power. With Traccar, Home Assistant's integration or both; not the native API configuration, which needs its connection up to be useful. (2026-11-20, 2026-11-21)
- **Detect hardware variants at run time where possible** (the owner's direction): the co-processor's version and the motion sensor's ID already are; what ESPHome fixes at build time (the modem's pins) stays a substitution. (2026-11-20)

## Reworked on 2026-11-22

From a design review before the side-by-side drives, at the owner's go-ahead.

- **Trips decided once per car.** `trip_tracker` (board package) takes fixes straight from `freematics_link` and movement from the motion sensor, and decides trip starts and stops; each `tracker_uplink` samples its fixes for its server (interval, turns, heartbeats) and keeps its own queue. Traccar and Home Assistant can no longer disagree about a trip, and standby asks the trip tracker instead of a registry of uplinks.
- **Protocols are transports.** Each uplink sends through a `Transport` (`transport.h`): Teltonika and Freematics over UDP (`udp_transport.cpp`), compact batches to a webhook (`webhook.cpp`); `transports.py` lists them with their own settings. A new protocol is a class, its codec header and an entry there.
- **The motion sensor is a component** (`icm426xx`): the YAML lambdas, globals and scripts are gone. Awake it streams 100 samples a second through the chip's FIFO: a motion binary sensor (movement), an impact sensor (each impact's peak beyond gravity, `motion.h`, tested on the host) and the chip's temperature. Before sleep, `icm426xx.arm_wake` sets wake-on-motion as before.
- **Extras on records**: temperature, cellular signal (the modem's `AT+CSQ`, no data) and impacts ride along with starts, stops and heartbeats, in a tagged block of the compact format that readers skip when they don't know a tag, and as GH3000 IO elements and Freematics PIDs for Traccar. Before sleeping, the dongle says when it reports next, for the integration's Reporting sensor.
- **GNSS restart**: after 10 minutes without a fix, `ATGPSOFF` then `ATGPSON`, as the telelogger does (co-processor commands; nothing reaches the bus).
- **Set aside** ([backlog.md](backlog.md)): Bluetooth presence (who's in the car), GPX tracks, the SIM7070's own GNSS, its power-saving modes, settings in the webhook's answer. Remote commands: not wanted.

Once this project is stable (after its first release, with the components proven in the cars for a few weeks), the components useful beyond this dongle move to a repository of their own, with their own documentation and tests, and are then offered to ESPHome itself. Until then they live here, and stay generic: nothing in them names this dongle (the component checklist in [development.md](development.md) checks it).

| `freematics_link` | Stays here | It speaks the Freematics co-processor's own commands |

## Phases

1. **Phases 0 and 1: cellular, GPS to Traccar, Wi-Fi first** (built). Back up the stock flash (`esptool.py --port <port> read_flash 0 0x1000000 stock-car1.bin`). Paste `examples/car-traccar.yaml` into a new device in ESPHome Device Builder, set `traccar_host` and `traccar_device_id` (the device's existing Traccar identifier works), add the secrets, open UDP 5027 on the Traccar server, and install over USB from the browser. On the bench, watch the USB log: PPP up, `ATGPS` fixes, records queued, "Traccar acknowledged". Then drive: the trip in Traccar with sharp corners, a stop record, heartbeats while parked; Wi-Fi at home switching LTE off and back on when leaving. Read the real data use from Hologram after a few days. *Exit:* a week of commutes in one car with every trip complete in Traccar and data use near the estimate in [configurations.md](configurations.md).
2. **Phase 2: `freematics_link` component.** Moves the co-processor UART, the GNSS parsing and a GNSS time source into C++, adds battery voltage from `ATRV` and the co-processor version from `ATI`. *Exit:* the same behavior without the lambda.
3. **Phase 3: store and forward on microSD.** The Traccar uplink's in-memory queue (300 fixes) survives coverage gaps but not a reboot or a long outage; move it to the SD card. *Exit:* three forced outages and two reboots with nothing lost.
4. **Phase 4: vehicle data, passively.** Researched in [vehicle-data.md](vehicle-data.md): the co-processor's only listening mode (`ATM1`) isn't documented as silent, and a CAN controller that isn't silent acknowledges frames and, at a wrong bit rate, sends error frames. Nothing is built until Freematics confirms a listen-only mode; both cars' gateways may leave little to hear anyway. Active OBD requests only later, as a separate, carefully tested step.
