# Changelog

All notable changes to this project are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses [Semantic Versioning](https://semver.org/).

## [Unreleased]

First release: ESPHome on the Freematics ONE+ Model B in place of the stock telelogger firmware, reporting GPS tracks to Traccar in a compact, acknowledged format (about 12 KB per hour of driving), or live to Home Assistant, with records and logs kept on the SD card and the device asleep while the car is parked. Vehicle data follows; nothing is sent to the vehicle bus.

### Added

- Traccar configuration (`examples/car-traccar.yaml`, the `tracker_uplink` component): fixes go to Traccar as Teltonika GH3000 records over UDP, about 19 bytes each with altitude (`traccar_altitude: "false"` leaves it out, 2 bytes less). A record every 10 s while moving and on every sharp turn, one when a trip starts (3 fixes in a row at 6 km/h or more, 50 m from where the car was parked, and only within 5 minutes of the motion sensor feeling the car move, so GPS drift in a garage or a house starts no trip, on OBD or USB power) and stops (after 3 minutes below 6 km/h), and a heartbeat every 15 minutes while parked, with battery voltage, the dongle's temperature and the cellular signal on starts, stops and heartbeats (Traccar shows the last two as `io72` and `io205`); all adjustable. Trips are decided once in the board package (`trip_moving_speed`, `trip_start_fixes`, `trip_start_distance`, `trip_start_motion`, `trip_stop_delay`), so Traccar and Home Assistant always show the same trips. Records are batched every minute, Traccar acknowledges each batch, and unacknowledged records are kept (up to 300) and sent again, so coverage gaps lose nothing. A Traccar device that used the Freematics protocol keeps its identifier. Its logs show in ESPHome Device Builder over Wi-Fi (it needs a `freematics_api_key` secret).
- Home Assistant integration configuration (`examples/car-ha-integration.yaml`, `packages/uplink-ha-webhook.yaml`): the same tracking sent to Home Assistant's [Freematics integration](https://github.com/raetha/ha-freematics) through a webhook (Nabu Casa's cloud or Home Assistant's own address), as compact batches of about 11 bytes a record (sent as base64 text, so they pass through Home Assistant Cloud) over HTTPS, every 2 minutes and at once on trip starts, stops and heartbeats, each acknowledged by Home Assistant. Each dongle has its own webhook: its URL goes in a secret named in the device config's `ha_webhook_url`. It can run beside the Traccar uplink, to report to both (uncomment `uplink-ha-webhook.yaml` in the Traccar example and set `ha_webhook_url`). The webhook URL never appears in the logs.
- The SD card's log can be downloaded over Wi-Fi without taking the card out (`sd-logs-download.yaml`): `http://<device>.local/log` and `/log.1`, behind a username and password, on ESPHome's bare HTTP server (about 8 KB of memory while a download runs, nothing over cellular). A "Stay awake" switch in Home Assistant (`standby.yaml`) holds off sleep for up to 30 minutes (`standby_stay_awake`) to download the log or update the dongle, then turns itself off.
- Impact detection: the motion sensor reads 100 samples a second while the dongle is awake, and an impact beyond 4 g (`impact_threshold`; hard braking is under 1 g) is reported at once with its peak, to Home Assistant as an Impact event to automate on (telling the family, calling for help) and to Traccar as `io247`.
- The GPS is switched off and on again after 10 minutes without a fix (`gnss_restart`), as the stock firmware does, so a receiver that stops producing fixes recovers on its own.
- Records carry a trustworthy time: after deep sleep the dongle's clock runs on but drifts by a minute or more over a night, so until SNTP or a GPS fix has set it again nothing is recorded, and a clock set back never makes an extra heartbeat or ends a trip. (A record stamped minutes ahead would have made Home Assistant ignore the next minutes of records as repeats.)
- Before sleeping, the dongle tells Home Assistant's integration when it will report next (its next heartbeat wake), so the integration can tell a parked car from a dongle that has gone quiet.
- Traccar's Freematics protocol, the one the stock firmware used (`traccar_protocol: freematics`, `traccar_port: "5170"`), to check a server with a protocol known to work: no acknowledgements and about four times the data, so not for everyday use.
- Home Assistant configuration (`examples/car-home-assistant.yaml`): the native API dialled from the device (Home Assistant 2026.10 or later) through a WireGuard tunnel, with latitude, longitude, speed and diagnostics sent only on real changes, and a template device tracker in Home Assistant (docs/home-assistant.md). Uses far more data than the Traccar configuration (docs/configurations.md).
- The example configs are complete on their own: paste one into ESPHome Device Builder, set a few substitutions and secrets, and build; the packages and components come from GitHub. Every optional setting is listed in the example, commented out with its default, ready to uncomment. Over-the-air updates are encrypted with the device's API key.
- A board package for the Freematics ONE+ Model B (`packages/freematics-oneplus-b.yaml`): the cellular modem, the co-processor link with the internal GPS, the motion sensor (ICM-42627), microSD, battery voltage, and diagnostics in Home Assistant (cellular signal, heap, uptime, reset reason, battery voltage), each sent only on a real change. Opening the device's logs shows how it's doing right away: uptime and why it last restarted, the co-processor's version, the GPS fix, and how many records Traccar has acknowledged and when it last answered.
- Cellular over LTE with the SIM7070G (`modem_model: SIM7600` for a SIM7600, untested): the module is started with a 200 ms power-key press and given 8 seconds to start before ESPHome's modem component talks to it; if it doesn't answer, every third try switches it off first with a long press, so a stuck module recovers without unplugging the dongle. At its first answer after each start of the device its serial speed is fixed at 115200 and it's restarted (`AT+CFUN=1,1`), as it keeps power across updates and crashes. It's restarted the same way after a dropped connection, and after three answers in a row that never led to a connection, since the SIM7070 refuses to connect again until it is. Otherwise it's switched to full functionality (`AT+CFUN=1`), as ESPHome's modem component leaves the SIM7070's SIM off after setting the APN. Adjustable with `modem_rx_pin`, `modem_tx_pin`, `modem_pwrkey_press`, `modem_pwrkey_tries`, `modem_boot_wait`, `modem_pwrkey_wait` and `modem_restart_on_boot`.
- GPS from the dongle's internal receiver, read through the co-processor by the `freematics_link` component, which also resets the co-processor at boot and can report its version, the GPS fix and the battery voltage it measures as sensors. Nothing is sent to the vehicle bus: only commands the co-processor answers itself.
- The clock is set from GPS, which costs no data; network time is only the fallback, synced every 12 hours (`sntp_interval`); ESPHome's default of every 15 minutes would cost about as much data a day over LTE as the tracking itself.
- Wi-Fi first: while a known Wi-Fi network is connected LTE is off, and it comes back when Wi-Fi drops. At start the device waits up to 10 seconds for Wi-Fi (`modem_wifi_wait`) before starting the cellular module, so at home the module isn't started at all. Each network keeps its own DNS servers, so names resolve whichever one is in use. While the car is moving with no Wi-Fi connected, the device stops searching for Wi-Fi (less radio noise beside the GPS antenna) and starts again once the car has been still for 30 seconds or has no GPS fix; a hotspot connected before driving off is kept (`wifi_pause_speed`, `wifi_resume_after`). Parked where no known network is found within 2 minutes, it stops searching until the car has moved (`wifi_search_time`); a network that was connected there and dropped (an access point restarting, a power cut) is searched for again after 1, 2, 4 and 8 minutes, then every 15. Wi-Fi power saving is `light` (`wifi_power_save: none` for an access point that keeps dropping the device). For bench tests, `lte_on_wifi: "true"` keeps LTE on beside Wi-Fi.
- Optional SD card packages: `sd-card.yaml` mounts the card; `sd-traccar.yaml` keeps every record on it until Traccar acknowledges it (up to 50,000, about 140 hours of driving), so a restart or a long time without coverage loses nothing; `sd-logs.yaml` writes the device's log to the card (two files of 1 MB at most), for finding out what happened away from Wi-Fi. The log and the stored records are each written by a task of their own, so the device never waits for the card (`traccar_store_writer_task: "false"` writes records from the main loop instead); records are synced to the card every 30 seconds (`sync_interval`) and before a planned restart or sleep. The `sd_card`, `file_queue` and `file_logger` components behind them work on any ESP32 board.
- Sleep while parked (`packages/standby.yaml`, optional in the Traccar and Home Assistant integration configurations): once the car has been off and still for 10 minutes, the device sends what it has, switches the cellular module, GPS and co-processor off and sleeps, waking for a moment every minute to check the 12 V voltage and the motion sensor. It stays awake again as soon as the car is on (its 12 V system charging, 13.2 V or more) or moves (towing, someone getting in; `standby_motion_mg`, 150 mg; awake, `motion_threshold` sets what counts as movement), and wakes fully every 6 hours to report one record. Before sleeping it waits for every uplink (Traccar, Home Assistant or both) to deliver what's waiting. Its one-minute checks don't count towards ESPHome's safe mode. Powered over USB instead of the OBD port, it sleeps once the motion sensor has felt nothing for 10 minutes and wakes on motion or for the heartbeat; tap the dongle to wake it for an update (`standby_on_usb: "false"` keeps it awake on USB, for a bench). The motion sensor is recognised by its ID: the Model B's ICM-42627 is supported, and without a supported sensor the device wakes on voltage and heartbeats only. All adjustable (`standby_voltage`, `standby_after`, `standby_check`, `standby_heartbeat`).
- Beeps, like the stock firmware: a short one when Wi-Fi or cellular comes up (at most once in 10 minutes, so a network that keeps dropping the device doesn't beep every minute), and a longer one once the firmware has started. `beep_on_network: "false"` and `beep_on_boot: "false"` turn them off.
- The Traccar server settings the configuration needs (docs/configurations.md), and `scripts/traccar_check.py`, which checks from any computer that a Traccar server answers the dongle's packets (port forwarding, device ID; `--protocol freematics` for the Freematics port).
- Bench tests, each pasted over the config for one install (docs/bench-tests.md): `bench-modem-probe.yaml` talks to the cellular module the way Freematics' library does and logs everything it answers; `bench-obd-listen.yaml` listens to the OBD port for one minute without sending anything to the car, the first step towards vehicle data.

### Internal

- The examples list the settings an optional package requires (`sd_log_password`, `ha_webhook_url`) among the commented-out settings, with an example value.

- Documented the board's lack of a clock chip and ESP-IDF's steadier sleep clock option, set aside for now.

- The components meant for other boards (SD card, file queue and logger, motion sensor, trips and uplinks) name nothing specific to this dongle, ready to move to a repository of their own and then to ESPHome once the project is stable.

- Trips are decided by a `trip_tracker` component, once for every uplink; each `tracker_uplink` sends through a transport per protocol (Teltonika and Freematics over UDP, the webhook), so a new protocol is a class and a schema entry; the motion sensor is an `icm426xx` component instead of YAML lambdas, with its motion analysis tested on the host.

- The host tests build the components' plain C++ as C++20, as ESPHome builds the firmware.
- A simulated day through the tracking filter and encoder checks the data estimates (`tests/test_simulation.py`).
- CI also builds each example with its optional packages switched on.
- The Teltonika encoder is checked against a real Traccar server (`tests/test_traccar_server.py`, run when `TRACCAR_UDP` is set).
- Components follow ESPHome's own rules for components (clang-format, clang-tidy, no memory allocation while running, a component test config), checked in CI.
- Repository workflow: `dev`/`main` branches, changelog checks, `esphome config` and `esphome compile` of every example and component test in CI, test builds as pre-release tags, Dependabot.
